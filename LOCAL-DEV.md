# Running OpenRed locally

The API, its workers and the React app on a laptop, with a small sample of data and
**nothing copied from production**.

OpenRed had no `Dockerfile` and no `compose.yaml`, so unlike the other applications in the pilot
this one needed its environment built rather than reused. What this adds is that environment —
`Dockerfile`, `compose.yaml`, `local_dev/` — plus the dataset: one management command,
`measures/management/commands/seed_local.py`, and the public snapshot it plants.

Everything here is on the `federation` branch and nowhere else. OpenRed is not containerised in
production: it runs under gunicorn and supervisor on a VM (`gunicorn.conf.py`, `deploy/`), and
none of this proposes changing that.

## Why there is no production data in here

The personal data in this application lives in `auth_user`, `account_emailaddress`,
`measures_emaillog`/`measures_emailrun`, and the `owner` / `user` / `created_by` columns that point
at a user. The measurements, tracks, spectra, stations, projects, missions and weather rows carry
nothing about anybody.

That split is what makes a production extract unnecessary rather than merely undesirable:

- **The realistic half can be rebuilt from a public source.** A measurement in OpenRed is a number,
  a place and a moment — a gamma dose rate or a night-sky brightness, at a coordinate, at a time —
  and all three are published as open data. The sample uses real readings, at the coordinates in
  Spain where they were really taken.
- **The half that would have carried personal data is the half that is cheapest to invent.**
  Accounts, devices and projects exist here only as actors: somebody has to own a device and
  somebody has to have contributed, or every screen is empty. Any six made-up people do that as
  well as six real ones.

So there is nothing to anonymise, because nothing personal is copied in the first place. This is
ADR-0009's "everything in it is fixtures", applied to one application.

### Neither source is allowed to name anybody

Both public sources identify, or can identify, the person or the instrument behind a reading, and
`local_dev/fetch_public_sample.py` drops those fields **at fetch time** so they never reach this
repository or any local database. It keeps an allow-list per source and asserts that no field from a
deny-list survived; it also refuses any kept value that looks like free text, because free text is
where a name turns up when nobody is looking for it.

What is deliberately thrown away:

| Source | Dropped | Why |
|---|---|---|
| Safecast | `user_id` | `api.safecast.org/en-US/users/<id>` shows that contributor's name |
| Safecast | `device_id` | one physical instrument, therefore its owner |
| Safecast | `id` | the measurement's own page names whoever submitted it, so even the record id is a back-reference to a person. A salted one-way `ref` is stored instead, only so a later run can deduplicate |
| Safecast | `location_name` | free text a contributor typed |
| Globe at Night | `SQMSerial` | a photometer serial number: one instrument, one owner |
| Globe at Night | `SkyComment`, `LocationComment` | free text; in practice "my back garden at…". 8,830 of the 13,402 rows in the 2025 file have one |
| Globe at Night | `LocalDate`, `LocalTime` | a local clock plus a place is more identifying than UT |

## The two public sources

Both were checked by hand before being chosen, and both were tested without an API key.

**Safecast** — <https://api.safecast.org>, for gamma radiation. Volunteer CPM readings with
coordinates and timestamps. **CC0 1.0**: *"Safecast data is published under a CC0 designation … the
data is free and open for anyone to use under any circumstance"* (<https://safecast.org/data/>).
No key needed, verified by request. Attribution is not required under CC0 and is given anyway.

**Globe at Night** — <https://globeatnight.org>, for light pollution. Volunteer naked-eye and SQM
night-sky-brightness observations, one CSV per calendar year. **CC BY 4.0**: *"Globe at Night data
is made available under a Creative Commons Attribution 4.0 International License"*
(<https://globeatnight.org/maps-data/>). Attribution **is** required: *Globe at Night,
<https://globeatnight.org>; files generated by Dennis L. Ward, © Copyright 2007 University
Corporation for Atmospheric Research.* No key needed, plain CSV download.

**EURDEP and the CSN's REA network** were the institutional alternatives and are not used. EURDEP's
data sits behind a registration for authorised users, and the CSN publishes its station readings as
a web map rather than as a downloadable open dataset. Safecast is the one of the three that is both
open and fetchable, and unlike the other two it is citizen-collected, which is what OpenRed is.

### What is real and what is not

Worth being precise about, because a development dataset that looks measured but is not is worse
than an obviously fake one.

| | Real | Invented |
|---|---|---|
| Radiation value | yes — the CPM is as Safecast published it, kept in `raw_data.source_value` | the dose rate is derived: CPM ÷ 334, Safecast's own constant for the LND 7317 tube. Not a calibrated figure |
| Sky brightness | yes — mag/arcsec² from the SQM reading, in `legacy_data.sky_brightness_mag_arcsec2` | `lux` is derived from it by standard photometry. `cct` and the CIE coordinates are left **null**: Globe at Night does not publish them, so nothing is invented to fill them |
| Coordinates, timestamps | yes | unless `--dates shifted` is in effect (it is, by default) |
| Track shape, distance, speed | yes — see below | which account, device, mission and campaign a track belongs to |
| Station readings | the values are real | the schedule is not: a station's series is generated relative to now |
| Spectra | no | entirely synthesised: a Compton-like continuum plus a K-40 photopeak at 1460 keV. Physically shaped, so the screens draw something recognisable; draw no conclusion from the numbers |
| Weather | no | synthesised, and labelled so in `weather_data.note` |
| People, devices, serials, projects, missions, campaigns | no | all invented. Serials are prefixed `LOCAL-` so none can be mistaken for a real instrument |

**The tracks are real routes, and that is not an accident.** Sorted by their real capture time,
consecutive snapshot records sit a median of about 1 km apart, because the fetch script keeps one
reading per ~1 km cell: what survives of each volunteer's drive is that drive's shape, in order.
`seed_local` therefore cuts tracks wherever the step between two readings exceeds 30 km, 6 hours, or
an implied speed of 45 m/s, and the resulting geometry, distance and average speed are all real.

Grouping by region instead — the obvious first idea — produced single "tracks" 1,900 km long,
because one region holds drives from different years, and every distance and speed derived from them
was nonsense. The implied-speed cut matters for a second reason: dropping Safecast's `device_id`
means two people driving different roads in the same area at the same time arrive interleaved, and
without it they merged into one zig-zagging track whose average speed came out at 830 km/h.

**The public sources publish bad rows, and they are filtered at fetch time.** The 2025 Globe at
Night file has `SQMReading` values of 1.0 and 3.0 — night-sky brightness lives between about 16 and
22 mag/arcsec², and 1.0 is brighter than daylight. Seeding those unchecked produced a "brightest
sky" of 135,074 lux, above direct sunlight. One row has `Latitude` 0.0, in the Gulf of Guinea, filed
under Spain. The fetch script drops coordinates outside an Iberian box and discards an implausible
meter reading while keeping the observation, which still has its naked-eye magnitude.

## What you need

Docker. Node 20+ only if you also want the React app.

## Start it

```sh
docker compose up -d --build
docker compose exec api python manage.py seed_local
```

The first build compiles the `h3` PostgreSQL extension, so expect a few minutes once.

That is the whole API: PostgreSQL with PostGIS **and h3**, Redis, the API, the three `django-rq`
workers that `openred/settings.py` declares, and `rqscheduler`. Migrations run on start.

- API docs: <http://localhost:8020/api/docs/>
- Django admin: <http://localhost:8020/admin/>
- RQ dashboard: <http://localhost:8020/django-rq/>

**The ports are deliberately unusual.** A development laptop already has the other Ibercivis stacks
on 8000, 8010 and 5432, so this one takes **8020** for the API and **5436** for PostgreSQL and
collides with none of them.

**Mail is caught by `mailpit`, at <http://localhost:8026/>.** Nothing leaves the machine and no SES
credentials are needed. It has to be readable rather than printed, because
`ACCOUNT_EMAIL_VERIFICATION` is `'mandatory'` as in production: an account registered through the
app's own form cannot be confirmed without opening the link in that mail, and a link printed into a
container's log is gone the moment the container restarts. The seeded accounts do not need it — they
are created already confirmed — but registering is one of the things you will want to try.

The web interface is on 8026 because 8025 is taken by another Ibercivis stack.

### Why the database is not `postgis/postgis`

OpenRed needs **two** PostgreSQL extensions, not one. PostGIS, for the three `PointField`s in
`measures/models.py`; and `h3`, because `measures/views.py` calls the server-side function
`h3_lat_lng_to_cell` in raw SQL for the `h3-aggregation` endpoints **and for the PDF reports**,
which the frontend does call.

h3-pg is not in the `postgis/postgis` images, and it cannot simply be added to one: every
`postgis/postgis` tag is Debian bullseye, and `apt.postgresql.org` no longer serves a
`bullseye-pgdg` Release file, so `apt-get update` fails outright inside those images. They are also
amd64-only, so on an Apple-silicon laptop they run emulated. `local_dev/postgis-h3/` therefore
builds on `postgres:17-bookworm`, which fixes both: pgdg serves bookworm, and the image is
multi-arch.

The extensions are created by `local_dev/postgis-h3/enable-extensions.sh` on first initialisation,
in the application database and in `template1`. OpenRed has no `CreateExtension` migration — in
production a superuser enabled PostGIS by hand — so without that script the first migration fails.

## What the sample contains

`seed_local` creates, by default:

| | |
|---|---|
| **People** | 6 invented accounts: one superuser, one staff member who owns the projects and the stations, four volunteers |
| **Projects** | *Radiación gamma de fondo en España* (radiation, public), *Contaminación lumínica del cielo nocturno* (light pollution, public), and *Radiación en balsas de riego* — public: false and deliberately empty, so the empty states are reachable |
| **Missions, campaigns** | 3 missions, 4 campaigns. One campaign is password-protected, so the protected upload path can be exercised; the password is printed by the command |
| **Radiation** | ~223 measurements in 11 tracks, plus ~17 loose points with no track — which is `capture_mode='movement'` with `track=NULL`, what the model itself calls *"punto suelto a agrupar en track"*. Keeping them matters: the snapshot's whole upper value range, 88 readings above 200 CPM and up to 1026, sits in those fragments, because they come from fixed loggers rather than drives. Without them every dose rate falls in a 0.05–0.18 µSv/h band and the map's colour scale and the histogram have nothing to show |
| **Stations** | 2, on real measured coordinates, each with a recent series — one `online` and reporting up to now, one `offline` because it stopped three days ago, which is what gives the watchdog something to find |
| **Spectra** | 22, two per track, 1024 channels each. Synthesised |
| **Light pollution** | ~159 measurements from Globe at Night's 2025 Spanish rows |
| **Devices** | 7 instances of 4 real device models (bGeigie Nano, RadiaCode 103, a GammaStation M5, an SQM-LE). The two station devices get an ingest token, printed once as in production |
| **Weather** | 20 synthesised cache rows, keyed on H3 resolution 8 as the production code does |

Options:

```sh
python manage.py seed_local --measurements 350   # up to what the snapshot holds
python manage.py seed_local --dates real         # see below
python manage.py seed_local --no-spectra         # faster
python manage.py seed_local --reset              # remove what a previous run created
```

Re-running it is safe. `--reset` deletes the invented accounts and the domain rows.

### About the dates

Both sources publish with a lag, and a long one. Safecast's Iberian coverage was driven between 2014
and 2025; Globe at Night publishes a calendar year at a time, so its newest file is up to a year old.
With the real dates, every screen that counts "this month" shows zero.

By default `seed_local` slides each set forward as a block, keeping the real intervals between
records, so the newest lands today. `--dates real` keeps the sources' own dates instead, at the
price of a home page whose last contribution was months ago. The command prints the shift it
applied.

**The station series is always recent**, whichever you choose. A station is the one thing in OpenRed
that must have fresh readings or the watchdog, the "last 24 h" chart and the activity figures are all
empty, so its schedule is generated relative to now and only its values come from the snapshot.

`created_at` is `auto_now_add` on every one of these models, so every row would otherwise be stamped
with the moment the command ran, and every activity feed would show the whole history as having
happened in the same second. `seed_local` back-dates it to each row's own timestamp afterwards.

### Refreshing the snapshot

`local_dev/public_sample.json` is committed, so **seeding never touches the network**. To rebuild it:

```sh
python3 local_dev/fetch_public_sample.py               # 12 Safecast pages per region, GaN 2025
python3 local_dev/fetch_public_sample.py --pages 20
python3 local_dev/fetch_public_sample.py --gan-year 2024
```

The Safecast API caps `limit` at 25 however large a value you send — checked with 25, 100 and 1000 —
so `page` is what actually advances, and the script walks pages per region. It also returns a 500 on
some queries, so requests are retried and a region that keeps failing is skipped rather than
aborting the run.

## Accounts

Every account's password is `devpass12345` (`--password` changes it). The addresses are on the
reserved `.invalid` domain, so none of them can reach a mailbox.

| Account | Role |
|---|---|
| `admin@openred.invalid` | superuser, for `/admin/` |
| `rosa@openred.invalid` | staff; owns the three projects, the missions, the campaigns and both stations |
| `ada@`, `bruno@`, `chiara@`, `dani@openred.invalid` | volunteers with devices, tracks and measurements |

`ACCOUNT_EMAIL_VERIFICATION` stays `'mandatory'` as in production, so the seeded accounts are given
confirmed `EmailAddress` rows and can sign in at once. Each also gets a DRF token, which is what the
API authenticates with.

**An account you register yourself is a different matter**, and the failure is confusing: sign-in
returns `non_field_errors: El correo electrónico no ha sido verificado` and nothing on screen says
where to confirm it. Open <http://localhost:8026/> and click the link in the mail. Registering also
puts an address that is **not** on `.invalid` into the database, which is exactly what
`seed_local`'s guard looks for, so the next `seed_local` or `seed_local --reset` will refuse until
you pass `--force` or delete that account. That is the guard doing its job; it cannot tell your own
test registration from a database it should not touch.

## The React app

[`Ibercivis/openred-react`](https://github.com/Ibercivis/openred-react), branch `federation` — note
that its default branch is `master`, not `main`. See `LOCAL-DEV.md` there. The short version:

```sh
npm ci          # NOT npm install: see that file for why
npm start       # http://localhost:3010
```

It reaches this API through its dev server's proxy, which now defaults to `http://localhost:8020`.
**It used to default to `https://api.open-red.es`** — production.

## Known issues, found while setting this up

Pre-existing, reproduce without any of this tooling, and only the ones marked *fixed here* were
touched.

1. **`requirements.txt` cannot be installed, and is not a complete manifest.** It is a `pip freeze`
   of a conda environment on a macOS laptop: `appnope` is macOS-only and `conda-package-handling`,
   `conda_package_streaming` and `pycosat` are conda's own plumbing. Worse, two packages the project
   imports are **missing** from it — `drf_yasg`, imported by `measures/views.py`,
   `measures/views_stats.py`, `missions/views.py` and `devices/views.py`, and `django_extensions`,
   which is in `INSTALLED_APPS`. Django cannot start without either. `cryptography` is needed too,
   by allauth's Google provider. *Worked around here:* `local_dev/requirements-pilot.txt` is the
   container's list, pinned to the same versions wherever `requirements.txt` names one. The
   repository's own file is left alone.

2. **Migration `measures/0002_enable_h3_extension` stopped every migration run on a server without
   h3.** *Fixed here.* Its comment said a failure in a test environment was acceptable, but
   `CREATE EXTENSION IF NOT EXISTS` only suppresses the error when the extension is *already
   created*; with h3 absent from the server, PostgreSQL raises `NotSupportedError` and the whole run
   stops, so a fresh database could not be migrated at all. It now tries, logs and continues — which
   is what the comment always claimed — and a server that has the extension still gets it created,
   so production behaviour is unchanged.

3. **The frontend calls five endpoints that do not exist on this branch.** Pre-existing, and nothing
   to do with the dataset. Measured against the running environment on 12 November 2026; `…/compact/`
   used to be listed here and was wrong — see the note under the table.

   | Endpoint | Status |
   |---|---|
   | `/api/stats/activity/`, `/api/stats/records/` | do not exist on any branch. `StatsViewSet` has only `global` and `heatmap` |
   | `/api/missions/`, `/api/campaigns/` | only the **nested** routes exist (`/api/projects/<id>/missions/`, `/api/missions/<id>/campaigns/`). The flat lists 404, and the frontend quietly substitutes `mockMissions` / `mockCampaigns` |
   | `/api/profile/` | does not exist; `users/urls.py` registers only `users` |

   **`…/compact/` is not one of them, and an earlier version of this file said it was.** It is on
   this branch and it is served. Measured on 12 November 2026:

   ```sh
   curl -s http://localhost:8020/api/radiation-measurements/compact/
   # {"fields":["id","lat","lon","dose_rate"],"rows":[[1,43.055538,-7.555707,0.10479], …
   curl -s http://localhost:8020/api/radiation-measurements/h3-aggregation/
   # {"resolution":8,"hexagons":[{"h3_index":"88397050adfffff","measurement_count":396, …
   ```

   `…/light-pollution-measurements/` answers the same on both. Which one the map asks for depends on
   zoom: `useMeasurementsByZoom.ts:322` in the React app calls `…/compact/` at zoom ≥ 15 and
   `getH3Aggregation` below it, so both of the map's data paths work here. What `…/compact/` is
   genuinely absent from is `origin/main`, which is a different claim — the branch the integration
   works on is not `main`, and conflating the two is what produced the wrong row.

   **The mock fallback is the trap here.** `src/services/api.ts` catches a failed measurements,
   missions or campaigns call and returns invented Zaragoza data with a `console.warn`. A screen full
   of plausible points is therefore not evidence that seeding worked. Check
   `/api/radiation-measurements/count/` instead, or look for `raw_data.source == "Safecast"` on a row.

4. **`measures/management/commands/add_measures.py` is broken, and would write to whatever database
   the settings point at.** It prints `device.name`, and `Device` has no `name` field, so it raises
   `AttributeError` before creating anything. It also defaults to `--device-id 1 --user-id 1`, has no
   `DEBUG` guard and no host guard, and `time.sleep(1.0)` between 1000 iterations. It is a random
   walk, not public data, and `seed_local` does not use it. By contrast `seed_local` refuses to run
   with `DEBUG=False`, and refuses a database holding accounts it did not create unless given
   `--force`.

5. **`openred/settings.py` logged every SQL query unconditionally.** *Fixed here*, minimally: the
   `django.db.backends` level is now `config('DB_LOG_LEVEL', default='DEBUG')`, so the default is
   unchanged and `compose.yaml` sets it to `INFO`. Django only emits these when `DEBUG` is true, so
   production was never affected — but the query log completely buried the output of
   `seed_local` and of every other management command.

6. **Logging into `/admin/` broke sign-in on the React app.** *Fixed here.* Two settings had to
   move, and the second is the one that mattered:

   `SessionAuthentication` is in `DEFAULT_AUTHENTICATION_CLASSES` so the DRF browsable API works
   while logged into the admin. But once it authenticates a request from the session cookie, DRF
   enforces CSRF — and the React app authenticates with a token and never sends an `X-CSRFToken`
   header. **Cookies ignore the port**, so merely having logged into `/admin/` on
   `localhost:8020` sent that `sessionid` to the app on `localhost:3010`, and every write came back
   `CSRF Failed: CSRF token missing.` It is now `config('ENABLE_SESSION_AUTH', default=True)`, so
   production and every other setup are unchanged, and `compose.yaml` sets it to `False`. With it
   off the session cookie is ignored, CSRF never engages, and token auth is the only path. Swagger
   at `/api/docs/` is unaffected — it authenticates with a token — and `/admin/` itself still works,
   because that is Django's own session login, not DRF's.

   Before that error you hit a different one from the same area:
   `CSRF Failed: Origin checking failed - http://localhost:3010 does not match any trusted origins`.
   Under `DEBUG`, `CSRF_TRUSTED_ORIGINS` was a hardcoded list naming only ports 8001 and 3000. It is
   now extended by `config('CSRF_TRUSTED_ORIGINS_EXTRA', default='')`, empty by default, and
   `compose.yaml` adds the 3010 origins. Redundant once session auth is off, kept because the
   hardcoded list is a real limitation for anyone who does leave it on.

   **Why `curl` will not reproduce either of these.** `curl` sends no `Origin` header and carries no
   session cookie, so the API answers 200 from a shell and fails only in a browser, and only for
   somebody who has visited the admin. To reproduce, pass `-H "Origin: http://localhost:3010"` and a
   logged-in session cookie jar.

7. **`TRACK_UPLOAD_NOTIFY_EMAILS` defaults to three named staff addresses** in `settings.py`.
   `compose.yaml` sets it empty so a local track upload cannot try to mail anybody.

8. **A measurement exactly on the equator or the prime meridian gets no PostGIS point.**
   `BaseMeasurement.save()` guards with `if self.latitude and self.longitude:`, and `0.0` is falsy.
   Found because Globe at Night had a row at latitude 0.0: it seeded with `location` NULL, and
   `stats/global` then returned `min_lat: null`. Harmless for Spain; wrong in principle.

9. **Deprecation warning on every management command** — allauth's
   `adapter.get_email_confirmation_redirect_url`. Harmless today.

## Limits of the local instance

- **The map needs a Mapbox token, which we do not have.** Every screen works without one. The map's
  deck.gl layers still compute, but there is no basemap under the points. Any token from a free
  Mapbox account in `REACT_APP_MAPBOX_TOKEN` fixes it; nothing in this repository needs one. The
  basemap is the **only** part of the map that is missing: its data endpoints are served on this
  branch, which an earlier version of this file got wrong — see known issue 3.
- **"Darkest sky" reads 0.00 lux.** Not a seeding bug: a natural dark sky really is about
  0.0008 lux, and `stats/global` rounds to two decimals. The honest figure is in
  `legacy_data.sky_brightness_mag_arcsec2`, around 21.6 mag/arcsec².
- **`urban_class` is left unset.** `measures/urban_class.py` classifies a point against the GHS-SMOD
  global raster, which `manage.py urban_class fetch` downloads on demand. It is large and not
  committed, so nothing here populates that column.
- **The weather worker is not exercised against its API.** 20 cache rows are synthesised; the rest of
  the measurements have no weather, which is what `fetch_pending_weather` exists to pick up. Running
  it would call Open-Meteo for real.
- **No track file is ever uploaded.** `seed_local` writes measurements straight into the database, so
  `Track.file` is null and `status` is already `completed`. The RCTRK parsers and the
  `openred-tracks` worker are therefore **not** exercised by seeding; to test those, upload a file
  through `POST /api/tracks/upload/` (`example_track.csv` is in the repository root).
- **The mobile client was not exercised.** `Ibercivis/openred-flutter` talks to the devices over BLE
  and needs hardware.
- **Re-seeding changes the primary keys**, so `/tracks/21` becomes `/tracks/32` after a `--reset`.
  The command prints the new project ids.
- **`media/` is not cleaned up** by `--reset`, which removes database rows only. Nothing the
  containers write reaches the work tree in any case: `compose.yaml` mounts a named Docker volume
  over `/app/media`, so uploads live in the volume and `docker compose down -v` is what clears them.
  Seeding writes no files at all.
